# Recent fixes and validation

## Launcher and room transport

The current launcher sources include the tested startup/cancellation and worker-ownership fixes. A cancelled or failed startup closes its owned sockets, listeners and partially started workers. A refused extra guest does not tear down existing teammates. Related regressions are in `launcher/tests/test_online_start_lifecycle.py`, `test_online_host_admission.py` and `test_online_race_e2e.py`.

The preceding capacity8 validation passed 129 launcher checks and 20 package checks, plus actual Windows loopback/TLS fixtures. These are inherited results for the same frozen launcher sources, rather than new gameplay or public-internet acceptance.

## Native carried-object tracking

Retired tracks can be reclaimed without losing stable placements. Prop traffic is bound to authenticated current-area player presence/generations, preventing stale or replaced peers from retaining authority. The capacity regression covers 3,100 distinct keys and repeated peer replacements. Core changes are in `client/src/sst_props.c`, `sst_remote.c` and engine patch 27; additional capacity probes are in `validation/`.

## Travel UI

Patch 28 fixes two problems reproduced in the actual Windows game:

1. Long arrival names hid their distinct room/layer/entry coordinates. Coordinates now appear first.
2. Keyboard focus cycled inside the arrivals child window. That child now shares navigation with its parent, allowing focus to reach **Teleport to selected arrival**.

The destination catalogue and native travel/safety checks are unchanged. Actual keyboard travel loaded Academy room 0, layer 1, entrance 2 with all three peers retained; native counters recorded one area load and no rejection.

## Windows hardware gameplay

The final 36,000-frame capture preset ran one actual game with three lightweight TCP peers, using the same native prop/pose receiver as normal multiplayer. The game and helper exited normally, with zero owned child processes and sockets remaining.

- Four complete characters rendered together before and after room travel.
- Ordinary movement and A-button input genuinely picked up and put down a small vase. The host forwarded 1,193 native descriptors for key 117/profile 496.
- A simulated peer replayed that session's captured key and relative transforms with fresh sequence/tick and the captured carry pose. The native game visibly rendered the vase supported by the partner's hands and following its movement.
- When descriptors stopped but poses continued, the vase restored to the floor. Fresh carry recovered. Invalid drawn-plus-carry context restored the vase safely; valid carry recovered again.
- Replaying the genuinely observed settled placement grounded the vase beside the partner; it stayed grounded after refresh stopped.

The peer sent 3,141 replay descriptors. No cold-import fixture or controller-side guest-memory writes were used. Reviewed image hashes and explicit test limitations are recorded in `validation/windows-gameplay.json`.

An earlier actual Windows pose-dropout check also showed all three avatars disappear when pose updates stopped and reappear with their original player IDs when updates resumed.

## Limits

This is representative one-game/simulated-peer acceptance, not independent full clients on separate PCs or a full campaign test. The Windows test did not independently probe the vase's actor-instance lifetime. Other object classes and throws remain untested. WSL software rendering remains incomplete even with a freshly compiled game library. Boss/miniboss sync remains off; consumable collection policy and private first-person/native lifetime restrictions are unchanged.

No new binary release, update-feed change, deployment or personal installation accompanies this source push.
