# Remaining co-op work

Updated November 11, 2026. This list separates observed problems from gameplay that still needs validation. The latest patch29 runtime passed one Windows game with three lightweight peers; it has not established separate full-client or campaign readiness.

| Priority | Work | Current evidence and next acceptance |
| --- | --- | --- |
| 1 | Pick up an object placed by another player | Twelve actual-bridge CPU cases pass across small pots, large pots and normal barrels, with both host and guest IDs. They cover local pickup/putdown, delayed packets, new-floor restoration and remote-owner departure. Next: use ordinary native input to pick up the remotely placed pot in a real game; verify the same actor instance, native held linkage, outgoing CARRY and a subsequent stable putdown. |
| 2 | Disconnect and ownership cleanup | Transport/roster replacement and remote departure have CPU and networking coverage. Your own client disconnecting while a remote object is presented follows a different clearing path; inspect and reproduce its floor-restoration behavior in an executing actor callback. This is a source-review concern, not a confirmed gameplay defect. Also test simultaneous pickup with different player IDs; deterministic packet ownership alone does not establish correct native held-state behavior. |
| 3 | Other objects, throws and breaking | Small/large-pot and reviewed normal-barrel adapters have CPU coverage. Actual gameplay evidence currently covers one small pot. Test large pots and normal barrels, then throws, collisions and destruction. Dynamic child identities and special/quest barrels are excluded from current prop synchronization. |
| 4 | Carrying through room and event changes | CPU gates cover load/session changes, pause and stale actor identities. Exercise native room transitions while carrying, cutscenes, death/reload and reconnects, checking that old descriptors cannot affect a new scene or actor lifetime. |
| 5 | Independent clients and campaign progress | Existing tests include real transport, a completed one-hour network soak and one full game with lightweight peers. Test independent full clients on separate PCs, internet delay/loss, reconnects and longer quest/save sequences. Preserve the one-full-game-at-a-time limit on the development PC. Boss/miniboss synchronization remains off; consumable pickups remain collector-only. |
| 6 | Linux/WSL rendering | Confirmed unresolved issue: the tested WSL software-Vulkan path misses title UI and parts of scenery. Rebuilding the game library did not fix it. Diagnose the renderer/driver path separately; Windows hardware evidence does not validate Linux rendering. |
| 7 | Fresh Windows build prerequisites | The pinned upstream Windows support ZIP also returned HTTP 404 during this continuation. Existing verified caches remain usable and are preserved. Find and verify an appropriate replacement source or provide an explicit offline-cache import before claiming that a clean PC can fetch every Windows prerequisite. The engine-source fallback does not replace missing release DLLs/tools. |
| 8 | Test startup and observation reliability | The controlled Windows fixture recorded an unavailable fixed guest address range; the ordinary runtime already has bounded restart handling. Improve fixture handling while retaining exact process ownership. Shared stderr can interleave scalar census records; parsing currently rejects these records. A separate observation channel would improve reliability. |

The original engine URL became unavailable during hosted validation. The source-restoration fallback now retrieves the identical pinned base from a public fork, applies the same patches and verifies the exact accepted tree and all 253 native source hashes. Seven local-Git regression cases pass normally and under optimized Python. The runtime itself did not change for this fix.

Runtime builds require 6 GB free on both Windows and Linux. Compiler CPU checks and actual gameplay retain their 3 GB reserves. A test stopped for memory pressure is recorded as incomplete. Source editing, fixed file-only checks and GitHub-hosted validation can continue while the development PC is busy.

The newly hardware-tested patch29 runtime still needs an isolated portable package with matching source before installation or public binary publication. The existing accepted travel9 portable retains its earlier runtime; source pushes do not update installed games or the release feed.
